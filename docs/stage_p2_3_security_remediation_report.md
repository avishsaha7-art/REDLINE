## 2. Independent Review Findings & Detailed Technical Analysis

### 2.1 BLOCKER-1 (CRITICAL): `LocalDevelopmentBackend` Does Not Provide Filesystem Isolation

#### The Finding
The review found that the initial plan's Requirement REQ-3 claimed:
> *"Actual filesystem boundary enforced... `SandboxPolicy.sandbox_root` and `allowed_workspaces` are pinned to the real canonical path... `resolve_and_validate_cwd` enforces strict boundary confinement with fail-closed semantics."*

The review demonstrated that this claim is fundamentally false.

#### Technical Analysis & Repository Code Verification
Inspection of [`backend/sandbox/backend.py`](file:///p:/REDLINE/backend/sandbox/backend.py) and [`backend/sandbox/capabilities.py`](file:///p:/REDLINE/backend/sandbox/capabilities.py) confirms the reviewer's finding in every detail:

1. **Explicit Class Docstring Warning (`backend/sandbox/backend.py:23-32`):**
   ```python
   class LocalDevelopmentBackend(SandboxBackend):
       """
       DEVELOPMENT_ONLY
       UNSAFE FOR UNTRUSTED PRODUCTION WORKLOADS

       - it executes code on the host environment
       - it does not provide OS-level filesystem isolation
       - it does not provide OS-level process isolation
       - it does not provide OS-level network isolation
       - it must never be used for untrusted repository execution
       - it exists for controlled local development/testing only
       """
   ```
2. **Explicit Declared Capabilities (`backend/sandbox/backend.py:34-45`):**
   ```python
   def capabilities(self) -> SandboxCapabilities:
       return SandboxCapabilities(
           filesystem_isolation="NOT_AVAILABLE",
           process_isolation="NOT_AVAILABLE",
           network_isolation="NOT_AVAILABLE",
           credential_isolation="ENFORCED",
           resource_enforcement="SUPPORTED",
           timeout_enforcement="ENFORCED",
           workspace_isolation="ENFORCED",
           cleanup_guarantee="ENFORCED",
           secure_untrusted_execution=False
       )
   ```
3. **Pre-Flight Check vs. Runtime Enforcement (`backend/sandbox/backend.py:71-136`):**
   The method `resolve_and_validate_cwd(working_directory)` validates only the **initial** working directory argument passed into `subprocess.Popen()`. Once the subprocess is launched, the OS kernel enforces standard host process permissions. The executing process can:
   - Call `os.chdir("..")` to traverse upward arbitrarily.
   - Access host files via absolute paths (e.g., `open(r"C:\REDLINE\backend\benchmark\dataset\evaluators\SEC-BENCH-001\test_secure.py")`).
   - Create symlinks to any accessible file or directory on the host.
   - Spawn sub-subprocesses with arbitrary working directories.
   - Use `ctypes` or `ctypes.windll` to invoke native Windows APIs directly.

**Impact on Benchmark:** If untrusted candidate code generated by Arm A or Arm B were executed in `LocalDevelopmentBackend`, candidate code could easily read `backend/benchmark/dataset/evaluators/`, reference patches, and test oracles. The candidate would have full access to the "answer key", destroying the validity of the benchmark.

### 2.2 BLOCKER-2 (CRITICAL): Dataset Commit Anchor Points to Wrong Baseline

#### The Finding
The initial plan specified:
```python
TRUSTED_DATASET_ANCHOR = {
    "commit_sha": "98f26d3f5f8267b70344c8c905f9b4f1cfb0cceb",
```

The review pointed out that Git status reveals that commit `98f26d3` was created during Stage P2-1 lint cleanup and does not contain the Stage P2-2 dataset files:
```text

?? docs/stage_p2_2_plan.md

?? tests/test_benchmark_dataset.py
```

#### Technical Analysis
- Git log verifies that commit `98f26d3` was created before any files in `backend/benchmark/dataset/` existed.
- The 12 benchmark tasks, JSON schema, manifest, fixtures, evaluators, and test suite are currently untracked files in the working directory.
- A preflight check validating `git status --porcelain` would either fail or, if untracked files were ignored, anchor to a commit that lacks the dataset entirely.
- Crucially, trusting an anchor commit that does not track the dataset allows any local modification to `fixtures/` or `evaluators/` to occur silently without invalidating the commit hash.

**Impact on Benchmark:** The dataset currently has no immutable identity in Git. A dedicated dataset commit and verified manifest SHA-256 anchor are required before benchmark execution.

### 2.3 BLOCKER-3 (HIGH): Evaluator Isolation Assumed Sandbox Enforcement

#### The Finding
The initial plan claimed that candidate code could only see `fixtures/<task_id>/` because the candidate sandbox root was pinned to an ephemeral copy. However, because the backend used was `LocalDevelopmentBackend`, the candidate process was not confined to that directory.

#### Technical Analysis
Physical separation of files on disk (copying only `fixtures/<task_id>/` into the ephemeral directory) is necessary but insufficient on its own. Without OS-enforced filesystem confinement, arbitrary code running inside that directory can read outside it. True isolation requires both:
1. Physical provisioning of fixtures only.
2. OS-enforced confinement (container mount namespace, DACL restriction, or sandbox boundary) preventing access to the rest of the host filesystem.

### Feasible Isolation Options for this Environment

1. **Option A: Docker Desktop / Engine for Windows (Recommended)**
   - Requires installing Docker Desktop with WSL2 backend or enabling Windows containers.
   - Confinement: Containers mount only the ephemeral directory (`-v <workspace>:/workspace:rw`). Evaluators and host files are unmounted and invisible. Read-only root filesystem (`--read-only`), network disabled (`--network none`), memory/CPU limits, dropped capabilities (`--cap-drop=ALL`).
2. **Option B: WSL2 Linux Distribution with Container Tools**
   - Requires running `wsl --install -d Ubuntu`.
   - Confinement: Podman, Docker, or `bubblewrap` (`bwrap`) / Linux user namespaces providing unshare of mount, PID, and network namespaces.
3. **Option C: Windows Native Process Isolation (AppContainer / Restricted Token)**
   - Uses Win32 security APIs (`CreateAppContainerProfile`, `CreateRestrictedToken`, Job Objects).
   - Confinement: Drops all administrative and write tokens; restricts filesystem DACLs such that only the ephemeral directory grants read/write, while all other host directories (including repository root and evaluators) grant ZERO access; Job Object enforces kill-on-close and resource quotas.
4. **Option D: Remote Secure Execution Sandbox Service**
   - Offload candidate subprocess execution over gRPC/HTTP to an external Linux/gVisor worker node that returns cryptographically signed `ExecutionResult` payloads (Stage 9.2 architecture).

### Mandatory Fail-Closed Policy
Because no OS-enforced sandbox runtime is currently operational on this host, **the benchmark harness must refuse untrusted candidate execution and report `OPERATIONAL_FAILURE`** until an OS-enforced sandbox backend is provisioned.

## 4. Key Architectural Corrections in Revised Plan

The implementation plan [`docs/stage_p2_3_plan.md`](file:///p:/REDLINE/docs/stage_p2_3_plan.md) has been rewritten to incorporate the following mandatory corrections:

### 1. Removal of False Isolation Claims
- All assertions that `LocalDevelopmentBackend`, `sandbox_root`, `allowed_workspaces`, or `resolve_and_validate_cwd` provide runtime filesystem boundary isolation have been completely removed.
- `resolve_and_validate_cwd` is explicitly identified as an initial working-directory validation gate, not a runtime security boundary.

### 2. Mandatory OS-Enforced Sandbox Prerequisite
- A genuine container-backed or OS-enforced sandbox (`SecurityLevel.SECURE`, `filesystem_isolation="ENFORCED"`) is established as a mandatory prerequisite for running untrusted candidate code.
- Untrusted candidate code is never executed via `LocalDevelopmentBackend`.

### 3. Fail-Closed Capability Gate
- The harness defines `enforce_sandbox_security_gate()`.
- If the configured backend does not provide enforced filesystem isolation, candidate execution is refused immediately, and the task/run verdict is set to `OPERATIONAL_FAILURE`.

### 4. Dedicated Dataset Commit Anchor
- Prerequisite Step 0 mandates committing the P2-2 benchmark dataset to Git (`chore: freeze P2-2 benchmark dataset v1.0.0`) and tagging it (`benchmark-v1.0.0`).
- The anchor definition is corrected to track:
  - `dataset_commit_sha`: The SHA of the dedicated dataset commit.
  - `manifest_root_sha256`: The verified SHA-256 digest of `manifest.json`.
  - Working tree cleanliness across `backend/benchmark/dataset/`.

### 5. Automated Security Isolation Test Matrix
- The test matrix in Section 6 is expanded to 12 explicit invariants and regression tests:
  - Traversal via relative paths (`../../evaluators/...`) blocked.
  - Absolute path access to evaluators blocked.
  - Symlink creation/escape blocked.
  - Subprocess spawning confined to sandbox boundary.
  - Cross-task workspace contamination prevented.
  - Context discovery (`discover_repository`) excludes all evaluator paths.
  - Insecure backend fails closed (`OPERATIONAL_FAILURE`).
  - Dataset commit anchor and manifest root verification.
  - Deterministic evaluator override prevention.
  - Operational vs. code failure separation.
  - Arm A vs. Arm B fair comparison enforcement.
  - Truthful non-statistical reporting.

### 6. Fair Comparison Enforcement (Section 55)
- **Identical Task Contracts:** Both arms receive the exact same `TaskContract`.
- **Identical Starting Context:** Both arms receive the exact same discovered context string generated from `discover_repository` on the clean fixture copy.
- **Equal Resource Ceilings:** Both arms are constrained by identical `ResourceBudget` ceilings (max runtime, max tokens, timeout). Arm B is wrapped in a budget monitor enforcing these limits.
- **Model Parameter Parity:** Pinned model version, `temperature=0.0`, fixed random seeds, and complete logging of request IDs and token metrics.
- **Identical Authoritative Evaluator:** Both arms' patches are evaluated by the same out-of-sandbox evaluator using clean fixtures and hidden tests.

### 7. Exact Verdict Distinctions Preserved
- `VERIFIED`: Public tests pass + exploit fails (neutralized) + secure acceptance passes.
- `REJECTED`: Regression detected, exploit persists, or secure acceptance fails.
- `INCONCLUSIVE`: Non-deterministic or contradictory test results, or ambiguous output truncation.
- `OPERATIONAL_FAILURE`: Infrastructure timeouts, process crashes, policy blocks, or missing secure sandbox capabilities. Infrastructure failures are never conflated with code rejections.
